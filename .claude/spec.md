# chan.py 量化研究项目 Spec

## 项目定位

本项目是在 `chan.py` 缠论结构计算库基础上构建的量化研究与交易系统。当前重点不再是堆叠多个实验模型，而是围绕一条可复现、可回滚、可解释的主线持续迭代：

```text
当前基准版本：decision_realtime_v2
当前主线模型：btc_futures_v2_bsp2_family
当前交易对象：币安合约主流币种
当前核心信号：15m 缠论二类买卖点族群
```

项目采用“vibe coding + 严格实验治理”的开发方式：交易想法可以快速提出，但任何代码改动必须有明确 spec、基准对照、验证结果、清理规则和 git 版本记录。

## 核心目标

1. 基于缠论二类买卖点族群提高交易机会覆盖率。
2. 保留 `decision_realtime_v2` 中已经验证有效的盈利路径。
3. 重点降低 `realtime_invalid_before_confirm` 和 `weak_no_confirm` 带来的亏损。
4. 保持自研回测、Freqtrade 模拟实盘、TradingView 展示页面之间的口径一致。
5. 保证 Rust 加速链路与 Python 原始链路在缠论元素计算结果上保持一致。

## 当前主线口径

### 入场

- 数据频率以 15m 缠论结构为核心。
- 入场信号来自二类买卖点族群。
- 入场时间使用信号可用时间，不额外推迟一根 15m K 线。
- 默认不使用旧概率硬过滤，以免交易频率被过度压缩。

### 标签

主标签：

```text
label_bsp2_family_valid
```

辅助标签：

```text
label_bsp2_identity_strict
label_pre_confirm_invalid
label_bsp2_realtime_path
label_bsp2_realtime_path_id
```

这些标签用于训练二级决策模型，但正式回测和模拟实盘不允许直接读取未来标签做决策。

### 出场

正式出场使用 `family_realtime` 实时状态机：

1. `bsp2_t3_overlap` 或 `2,3a` / `2,3b` 信号视为入场时第三段已经确认。
2. 普通二类族群先检查结构失效位。
3. 如果先回到原中枢目标，按回中枢目标出场。
4. 如果先走出第三段确认，移动保护止损，之后等待 15m 同级别任意反向买卖点出场。
5. 限定时间内既无确认也无回中枢，按弱确认超时出场。

### 仓位

结构风险定仓由 `ML/shared/structure_position_sizing.py` 负责：

- A 类信号可使用较大仓位。
- B 类信号使用中等仓位。
- C 类信号保留交易但降低仓位。
- 对确认前失效概率高、弱确认概率高、结构失效距离过大的信号降低仓位，而不是直接删除信号。

## 关键约束

以下内容是当前主线保护项，未经实验 spec 明确说明不得改动：

1. 不得随意改变第三段确认后的 15m `opposite_bsp` 出场路径。
2. 不得在回测决策中读取未来标签。
3. 不得为了提高收益牺牲交易频率而不记录原因。
4. 不得把临时脚本、smoke 结果、本地配置、数据库、日志提交到 git。
5. 不得在没有一致性验证的情况下修改缠论元素底层计算逻辑。
6. 不得把失败实验长期留在主线代码里。

## 数据流

```text
本地 K 线数据
  -> Python/Rust 缠论元素计算
  -> 二类买卖点族群候选生成
  -> 特征构建
  -> 标签生成
  -> 入场模型 / 二级决策模型训练
  -> 自研 walk-forward 回测
  -> Freqtrade 模拟实盘
  -> TradingView 展示和交易事件复盘
```

## 模块边界

| 模块 | 责任 |
|---|---|
| `BuySellPoint/`、`Bi/`、`Seg/`、`ZS/` | 缠论基础结构计算 |
| `RustCore/` | Rust 加速适配，必须保持结果一致 |
| `ML/routes/btc_futures_v2_bsp2_family/` | 当前正式模型路线 |
| `ML/shared/` | 跨路线复用的策略、仓位、阈值工具 |
| `Backtest/` | 自研回测框架与静态回测展示 |
| `TradingView/` | K 线、缠论元素、回测交易展示 |
| `user_data/strategies/` | Freqtrade 策略源码 |

## 实验开发流程

每次新实验必须按以下顺序推进：

1. 读取当前基准和最近结果。
2. 写入 `.claude/experiments/YYYY-MM-DD-experiment-name.md`。
3. 明确理论假设、代码范围、成功标准和失败清理方式。
4. 实现最小改动。
5. 跑编译检查、单元测试或 smoke 检查。
6. 跑年度 walk-forward。
7. 与 `ML/BASELINE.md` 对照。
8. 更新 `ML/EXPERIMENT_LOG.md`。
9. 失败实验删除代码和结果，成功实验合并登记。
10. 提交 git。

## 后续 Review & Simplify 重点

- 标签是否仍然对应真实可交易结构。
- 回测是否存在未来函数。
- 第三段确认后的盈利路径是否被破坏。
- 新特征是否带来实际区分能力。
- 是否出现重复计算或缓存失效。
- 交易频率是否被无意降低。
- 回测结果是否可复现。
- Freqtrade 和自研回测是否存在口径偏差。
- 文档、代码、模型登记是否一致。
